This tutorial shows how to use STICKS to reconstruct and inspect a campaign plan. Structured threat intelligence identifies techniques and relationships, while an executable procedure also needs concrete actions, parameters and environment facts. STICKS makes these choices explicit and checks candidates against a declared catalog. We will run the command line, inspect the planning interface, export a result and repeat the same computation. Planning does not execute an attack.

Start with the anonymous ZIP linked in the paper. Open a terminal in the extracted directory and run the workbench command shown here. The launcher installs the pinned dependencies on first use. Open the local address it prints. No model key is required. We will inspect the input, compute a result, export it, and repeat that same computation through the command line.

First use the command line to reconstruct campaign C zero zero four five, ShadowRay. The output directory keeps the procedural plan, derived environment and admission result. In this run, ten of ten compiled steps have an admitted realization. That result concerns the available catalog and the declared facts. It does not show that these procedures were executed or that they reproduce the historical actor.

Now reconstruct campaign C zero zero zero one. The same pipeline admits one of twenty seven steps and leaves twenty six unresolved. Read the unresolved techniques and their reasons. Missing catalog support remains visible. The tool does not silently fill these steps with plausible commands. This is why the campaign identifier, catalog version and full result matter more than a success label alone.

In the workbench, select ShadowRay from the campaign list. The default filter shows campaigns with the frozen inputs needed for enumeration. Set explicit limits for realizations, search states and candidates per step. These are computational bounds, not claims about how many procedures exist in the real world. Select Enumerate realizations to run the existing planning engine.

The summary reports sixty four complete realizations, but only one procedure assignment, one behavior contract and one causal structure. The sixty four schedules differ in the ordering of actions whose declared dependencies permit that variation. They are not sixty four independent behaviors. The search stopped at the realization ceiling, so search exhausted is false. The visible operational status remains not run.

Open Steps. Each row identifies a compiled source step and its technique, then separates raw candidates from assignments participating in complete realizations. The positions column shows where that step occurs across the returned schedules. A candidate count alone is not a count of executable alternatives. Use these rows to locate coverage gaps before proposing additions to the catalog.

Open Realizations to inspect a schedule, its templates, assumptions and fidelity ceiling. This example reports inspired fidelity. The declared composition uses benign laboratory implementations; the workbench is not certifying historical reconstruction. Different orders must respect the same fact dependencies. The exported result preserves the detailed graph and reachability record for inspection.

The proposal queue identifies declared procedure deficits and generation targets. Here it creates ten targets from the requested variant counts. Constructing this queue makes no model call. A generated proposal still needs admission under the same trusted contract, and an implementation witness before it can enter the operationally bound catalog. This view prepares work; it does not certify newly generated behavior.

Download the JSON. The interface shows the exact command for the selected campaign. Run the command line with from result and choose a new output filename. It reloads the bundled inputs, recomputes through the same service and compares the complete workbench object before writing anything. The additional comparison shown here confirms that the actual downloaded and recomputed JSON results are equal. Keep both files and the artifact version together.

Change the maximum realizations from sixty four to eight. The old result disappears and its download is unavailable. Enumerate again. The new result now reports eight schedules under the new bound. This prevents an export computed for earlier settings from being mistaken for the current request. The new digest identifies the new result.

To use another STIX two bundle, enter its campaign identifier and choose the JSON file in the admission panel. This example imports the pinned bundle. Inspect admitted and unresolved steps, then download the result. Repeat the same input through the command line and compare the complete JSON. No campaign action is executed.

This tutorial covered compilation, admission inspection, bounded enumeration and auditable export. A live campaign requires the separate laboratory workflow: provision, readiness checks, dispatch, independent observations and teardown. A planning certificate cannot replace that evidence. Follow the laboratory guide for the supported environment, and retain each run result separately. This narration is synthetic.
